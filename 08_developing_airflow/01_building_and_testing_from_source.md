# Building and Testing Airflow from Source

> [!CAUTION]
> Commands on this page can change or delete data and affect running deployments. Try them on a test or staging deployment first, and read the [disclaimer](../README.md#disclaimer). The guide is provided "as is", without warranty.

This page is for people who change Airflow itself: core, the Task SDK, a provider, the Helm chart, or the docs. The official contributor documentation lives in `contributing-docs/` and `dev/breeze/doc/` and is long and complete. This page is the short, opinionated path through it: which environment to use for which job, the exact commands, and the mistakes that cost contributors the most time. It also explains how this field guide relates to the official docs, and how to check the guide itself.

Paths on this page are relative to the root of an `apache/airflow` checkout. Commands were taken from the repository's `AGENTS.md`/`CLAUDE.md`, `contributing-docs/` and `dev/breeze/` on the `main` branch; check them against the branch you work on.

| | Official docs | This field guide |
| :--- | :--- | :--- |

If you fix behavior in Airflow, fix the official docs in the same PR. If a guide page goes stale because of your change, update it separately; the guide is not part of any Airflow release.

## 2. Repository layout

The repository is a **uv workspace**: one `uv.lock` at the root pins every dependency for every distribution, and each distribution has its own `pyproject.toml`.

| Path | What it is | Published as |
| :--- | :--- | :--- |
| `airflow-core/` | Scheduler, API server, Dag processor, triggerer, models, CLI, UI (`src/airflow/ui/`, React + Vite) | `apache-airflow-core` |
| `task-sdk/` | Dag authoring interface (`airflow.sdk`) and the task runtime (`src/airflow/sdk/execution_time/`) | `apache-airflow-task-sdk` |
| `providers/<name>/` | 100+ providers, each a separate distribution with its own tests and docs | `apache-airflow-providers-<name>` |
| `shared/<lib>/` | Small shared libraries (`configuration`, `logging`, `observability`, `secrets_masker`, `timezones`, …) | Not published on their own. Their sources are **symlinked** into consumers, for example `airflow-core/src/airflow/_shared/configuration` and `task-sdk/src/airflow/sdk/_shared/configuration` |
| `airflow-ctl/` | `airflowctl`, the API-based remote CLI | `apache-airflow-ctl` |
| `chart/` | The Helm chart | Helm chart |
| `devel-common/` | Shared test fixtures (`src/tests_common/pytest_plugin.py`) and test utilities | Not published |
| `dev/breeze/` | Breeze, the containerized dev and CI environment | Not published |
| `scripts/ci/prek/` | Static-check hook implementations | Not published |
| root `pyproject.toml` | The `apache-airflow` meta-package and the workspace member list | `apache-airflow` |

Consequences worth knowing:
* A change under `shared/` changes both core and the Task SDK. Run the shared library's own tests and the consumers' tests.
* Each distribution declares what it needs. `uv sync --project <dir>` gives you only that distribution's dependencies, which is how CI catches an undeclared import.
* Tests mirror sources: `airflow-core/src/airflow/cli/cli_parser.py` is tested in `airflow-core/tests/unit/cli/test_cli_parser.py`.

## 3. One-time setup

```bash
git clone https://github.com/<your_github_user>/airflow.git
cd airflow
git remote add upstream https://github.com/apache/airflow.git

uv sync                          # create .venv with core, task-sdk and the default providers
uv tool install prek             # the static-check runner (a pre-commit replacement)
prek install                     # run the fast hooks on every commit
scripts/tools/setup_breeze       # install the ~/.local/bin/breeze shim
```

Replace `<your_github_user>` with your GitHub account; work on a fork and push only there.

* **uv** manages Python versions, the virtual environment and the workspace. Supported Pythons on `main` are listed in `contributing-docs/07_local_virtualenv.rst`.
* **The breeze shim** (ADR 0017 in `dev/breeze/doc/adr/`) runs Breeze with `uv run --locked` from the `dev/breeze` folder of the **current worktree**, so every worktree gets the Breeze version that matches its sources. The older `uv tool install -e ./dev/breeze` pins one checkout globally and causes confusing mismatches when you have several worktrees.
* **Docker** (Docker Desktop, Colima or Docker Engine) is required for Breeze. Give it at least 4 GB of memory *(illustrative)*.

> [!TIP]
> On macOS, `uv sync` across the whole workspace can fail with `Too many open files`. Run `ulimit -n 2048` (add it to your shell profile), as `contributing-docs/07_local_virtualenv.rst` recommends.

## 4. Two environments, and when to use which

| Use | For | Not for |
| :--- | :--- | :--- |
| **uv on the host**: `uv run --project <dir> pytest …` | Fast unit tests, debugging in your IDE, scripts in `dev/` | Tests that need system libraries, MySQL/Postgres, Kerberos or other integrations |
| **Breeze**: `breeze run …`, `breeze shell`, `breeze testing …`, `breeze start-airflow` | Anything that must match CI, database backends, integrations, running the full Airflow, building docs | Quick edit-test loops when uv works |

The repository's agent instructions are strict about one point, and it is good advice for humans too: **don't run `pytest`, `python` or `airflow` directly on the host.** Either go through `uv run --project <dir>`, which uses the workspace's locked environment, or through Breeze. A bare `pytest` or `airflow` picks up whatever is installed in your shell's environment, possibly a released Airflow, and produces results that don't match CI.

If Breeze can't start (Docker missing or refused), stop and fix that. Don't build a substitute environment from a released Airflow; it won't contain your changes.

## 5. Running tests

`<PROJECT>` below is the folder with the `pyproject.toml` of the distribution under test, for example `airflow-core`, `task-sdk` or `providers/amazon`.

```bash
# One test, one file, one package, with uv
uv run --project airflow-core pytest airflow-core/tests/unit/cli/test_cli_parser.py::TestCli::test_arg_option_long_only -xvs
uv run --project airflow-core pytest airflow-core/tests/unit/cli/test_cli_parser.py -xvs
uv run --project providers/amazon pytest providers/amazon/tests/unit -xvs

# The same test in the CI image, when uv lacks a system dependency
breeze run pytest airflow-core/tests/unit/cli/test_cli_parser.py -xvs

# Against a different metadata database
breeze run --backend postgres pytest providers/postgres/tests/ -xvs
```

The test name in the first command is an example; substitute your own test.

Whole suites, as CI runs them:

| Goal | Command |
| :--- | :--- |
| Core tests, in parallel | `breeze testing core-tests --run-in-parallel` |
| Only DB tests / only non-DB tests | add `--run-db-tests-only`, or use `--skip-db-tests --use-xdist` |
| One provider's full suite | `breeze testing providers-tests --test-type "Providers[amazon]"` |
| Task SDK tests | `breeze testing task-sdk-tests` |
| Helm chart unit tests | `breeze testing helm-tests --use-xdist` (add `--test-type apiserver`, `--kubernetes-version 1.35.8`, …) |
| Provider code against a released Airflow | `breeze shell --use-airflow-version <version> --mount-sources providers-and-tests`, then `pytest providers/<provider>/tests/...` inside |
| What CI would run for your diff | `breeze verify` (add `--full` for everything except static checks) |

Conventions the reviewers will check (from the repository's `AGENTS.md`):
* pytest style, not `unittest.TestCase`; `@pytest.mark.parametrize` for input variants; `spec`/`autospec` on mocks.
* `@pytest.mark.db_test` on tests that touch the database.
* `conf_vars` from `tests_common.test_utils.config` for config overrides, `time_machine` for time.
* Every changed behavior has a test that fails without the change.
* Assert on structured log events, not on raw `caplog.text`.

SQLite is the default backend. Use `--backend postgres` or `--backend mysql` for behavior that differs by database, which includes most migrations and anything with row locking.

## 6. Running Airflow from your sources

```bash
breeze start-airflow
```

This builds the CI image on first use, starts a container with your sources mounted, and runs every component in a terminal multiplexer (`mprocs` by default, `--terminal-multiplexer tmux` to switch). The UI is on `http://localhost:28080` (not 8080), with user `admin` and password `admin`. Useful options:

| Option | Effect |
| :--- | :--- |
| `--backend postgres` / `--backend mysql` | Use a real database instead of SQLite. |
| `--executor CeleryExecutor` | Start with Celery workers. |
| `--load-example-dags` | Load the example Dags. |
| `--dev-mode` | Run the UI in development mode with hot reload. |
| `--use-airflow-version <version>` | Run a released Airflow instead of your sources, for comparisons. |
| `--integration <name>` | Start an integration container, for example `statsd` or `otel`. |

Put your own Dag files in `files/dags/` at the repository root; that folder is mounted into the container. Press `q` in mprocs to exit, then run `breeze down` to remove the containers and volumes. Use `breeze down --cleanup-mypy-cache` when mypy behaves strangely.

For a Kubernetes cluster, go through `breeze k8s` as well (`breeze k8s create-cluster`, `breeze k8s deploy-airflow`, and `kubectl` only via `breeze k8s shell ... -c '<command>'`). See `contributing-docs/testing/k8s_tests.rst` and [Kubernetes & Helm](../04_infrastructure_and_cloud/03_kubernetes_and_helm_chart.md).

## 7. Static checks with prek

`prek install` runs the fast hooks on each commit. Before you push, run them against your target branch:

```bash
prek run --from-ref main --stage pre-commit          # the regular hooks
prek run ruff --from-ref main                        # lint only
prek run ruff-format --from-ref main                 # format only
prek run mypy-airflow-core --all-files               # type-check core (also mypy-task-sdk, mypy-shared-<lib>, ...)
breeze run mypy providers/amazon/src                 # type-check a provider
```

Replace `main` with the branch your PR targets (for example `v3-4-test` for a 3.4 backport).

Hooks that catch contributors most often:
* `check-no-new-airflow-exceptions` refuses new `raise AirflowException(...)`. Raise a built-in (`ValueError`, `TypeError`) or a dedicated exception class.
* Apache license headers on every new file.
* Generated files must be regenerated, not hand-edited. The hook names which generator to run.
* `mypy-*` hooks use their own virtualenvs under `.build/mypy-venvs/` and never change your `.venv`.

## 8. Building the docs

```bash
breeze build-docs                                   # everything: slow
breeze build-docs apache-airflow                    # core docs only
breeze build-docs task-sdk
breeze build-docs amazon google                     # provider short IDs
breeze build-docs --package-filter 'apache-airflow-providers-*'
```

Output lands in `generated/_build/`. Spelling is checked during the same build, so one run reports both kinds of errors. `--clean-build` removes previous build artifacts; `--clean-inventory-cache` forces a fresh download of the intersphinx inventories. Most failures come from docstrings in autogenerated API pages; the generated `.rst` files sit under `generated/` so you can find the source line.

## 9. Branches and backports

| Branch | Purpose |
| :--- | :--- |
| `main` | All new work. Every PR targets `main` first. |
| `v3-4-test` | Where 3.4.x patch-release fixes are backported, usually by an automatic cherry-pick PR after the `main` PR merges. |
| `v3-4-stable` | What 3.4.x releases are tagged from (`3.4.0`, …). Read-only for contributors. This guide is checked against it. |

Providers are released from `main` on their own schedule, independent of core. Their changelogs are regenerated from `git log` by the release manager, so don't add newsfragments for providers. In `airflow-core`, add a newsfragment only for changes users must read before upgrading (see `contributing-docs/18_contribution_workflow.rst`).

## 10. Checking this guide against a new source

The guide's tools are standard-library Python plus PyYAML. Inside the Airflow repository, run them through the `scripts` workspace member rather than a bare interpreter:

```bash
mkdir -p /tmp/airflow-3.4
git archive origin/v3-4-stable airflow-core shared task-sdk chart | tar -x -C /tmp/airflow-3.4
uv run --project scripts python new_docs/tools/check_links.py
uv run --project scripts python new_docs/tools/check_docs.py /tmp/airflow-3.4
uv run --project scripts python new_docs/tools/build_ai_bundle.py --check
```

`check_docs.py` fails on any CLI command, flag or `[section] key` the guide mentions that doesn't exist in that source. Rules for writing pages are in `new_docs/AGENTS.md`.

## 11. Troubleshooting the dev environment

| Symptom | Likely cause | Fix |
| :--- | :--- | :--- |
| Tests pass locally, fail in CI | You ran a bare `pytest` against a different environment, or a non-DB test touches the database | Re-run with `uv run --project <dir>` or `breeze run`; add `@pytest.mark.db_test` |
| `ModuleNotFoundError` for a dependency in one distribution only | The import isn't declared in that distribution's `pyproject.toml` | Declare it; reproduce with `uv sync --project <dir>` |
| Breeze uses old code after switching worktrees | A globally installed Breeze | Re-run `scripts/tools/setup_breeze` to get the per-worktree shim |
| `breeze start-airflow` UI not on 8080 | It isn't meant to be | Use `http://localhost:28080` |
| Docker networking errors | Stale networks | `docker network prune`, then `breeze down` |
| mypy reports nonsense after a rebase | Stale cache | `breeze down --cleanup-mypy-cache` |
| Docs build fails on a page you didn't touch | Your docstring is rendered into an autogenerated API page | Look under `generated/` for the failing file, fix the docstring |

See also: [installation & Python](../04_infrastructure_and_cloud/01_installation_and_python.md) for installing released Airflow, and [testing Dags](../02_dag_authoring/03_testing_dags.md) for testing user code rather than Airflow itself.
